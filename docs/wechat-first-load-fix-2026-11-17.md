# 0.7.1 首次下载中断恢复

## 真机反馈

0.7.0 发布后，用户在 iPhone 微信里进入营地时看到：营地模型已接收约 1010 KB，随后连续 30 秒没有新进度而超时。用户随后确认第二次进入可以显示。这说明该设备能够加载模型，不能把一次 Chrome 手机仿真成功当作真实微信首访稳定的证明；暂时也不能据此确定微信、iOS 或 GitHub 链路的具体根因。

## 已确认的程序行为

- `loadModel` 原来只做一次下载，瞬态中断直接变成场景错误，必须用户重进或手动点重试。已成功的模型本来就可保留。
- 选完用户会立即准备当前单元音频；真实冷启动夹具在小屋模型被持有期间观察到一次整单元准备和 20 条音频请求。页面模型与后台音频各自限制并发，仍然会争抢同一条链路。
- gzip 传输长度与进度里的字节不一定相同；XHR 的 ArrayBuffer 在完整响应后才交给解析器。因此本补丁不把进度 KB 直接当作可恢复的字节偏移。

## 小步修复

1. 瞬态无进度、连接错误或 502/503/504 最多自动再试一次。取消、404、解析错误和整体期限不触发自动重试；整个下载与等待共享原有总预算，页面隐藏时不主动发起新尝试。
2. 自动恢复时继续显示加载层和简短说明，已完成的模型继续保留；两次均失败后才显示最终错误与手动重试入口。
3. 后台单元音频仅在营地已准备好且孩子进入听辨、拼写或跟读后启动。小屋、营地首次准备和营地任务总览期间不启动整单元预取。单个示范音仍可随时按需播放，家长主动准备完整离线包的行为保留。

## 验证边界

使用真实 HTTP 中途停流、连接中断和同 URL 第二次完整返回的夹具，核对完整字节、SHA256 和模型解析；检查两次失败有界、取消/404不重试、等待阶段取消与跨尝试总期限。单元测试之外，使用真实 Service Worker 检查冷启动场景与音频准备时序、实际 AAC 播放和三维不可用时的学习入口。

2026-11-18 本地验证结果：

- 全量 174 项单元测试与发布构建通过；下载恢复真实 HTTP 七项、发布包音频错峰十个检查点通过。
- 真实 SW 控制下首次营地半包停传，自动第二次取得完整 1,597,376 字节，SHA256 和 GLTF 解析正确；只有一次完整缓存写入，旧半包结束后未污染缓存，随后断网仍可完整读取。
- 该 SW 场景中旧后台 HTTP 在页面恢复后仍保持，服务器活动传输峰值为 2；不宣称页面取消能同步终止 worker 的旧传输。
- 发布包核心学习、真实三维点击、测试音源录音、存档导入/导出、完整离线和 390/768 布局通过；原手机加载恢复十二组检查继续通过。

可重复工具：`tools/browser-stall-recovery.cjs`、`tools/browser-sw-stall-recovery.cjs`、`tools/browser-scene-priority.cjs`。

本补丁改善的是程序遇到首次中断后的恢复和下载优先级，不声称消除了网络波动。实际微信首访仍以真机后续反馈为准；不清除用户列表、学习进度或录音。

遵循 ub-mode：先固定原来的单次失败与过早预取，再加有界恢复和推迟预取；保留已有下载、缓存、模型和存档边界。
