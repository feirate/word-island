# 0.6.4 慢网与缓存写入修复

0.6.3 发布后，用户的微信报“小屋模型下载超时”，默认浏览器也未成功显示。手机直接访问模型链接可以下载约 538 KB，因此不能把问题归结为手机无法获取模型，也不能将 Chrome 手机 UA 仿真等同于真实 iOS 验收。

## 本次证据

- 原小屋 GLB 为 1,825,956 字节；GitHub Pages 已使用 gzip，观测到传输长度约 576,781 字节。下载后 SHA256 与原文件一致。
- 不受 Service Worker 控制时，Chrome 的 arrayBuffer、Stream、XHR 三种路径都可以完整读取。顺序测试不能证明其中一种一定更快，也没有证据确认特定 iOS GET/Stream 系统缺陷。
- 旧加载器把 30 秒作为整个下载的期限。真实慢传测试在第 30 秒仍持续接收：此前收到 42 次进度，最后一次仅在 562ms 前，却仍然报超时。
- Service Worker 在等待 cache.put 完成后才把 Response 交给页面。真实夹具阻塞缓存写入 500ms 时，页面连响应头也无法获得；这会把缓存等待和网络下载混在一起。

## 修改

1. 下载短时限改为连续无进度 30 秒。有响应头或新增字节会重新计时；另有独立 180 秒总上限。两类超时、HTTP 错误、连接错误和主动取消分别记录。
2. 浏览器优先使用原生 XHR ArrayBuffer 读取，缺少 XHR 时回退 fetch。此举减少自定义网络流读取的兼容面，不据此声称已证明 iOS 的根因。完整响应到达后才交给 GLB 解析器。
3. Service Worker 立即返回网络 Response，完整缓存写入交给 event.waitUntil 后台完成；写入失败不挡住可用画面，离线准备仍需确认完整缓存成功。
4. 画面显示接收 KB 和耗时；错误可展开查看版本、下载阶段、已接收字节和失败原因。诊断不包含姓名、学习成绩或录音，不自动上传。
5. 导航改为优先网络重验证、离线时回退缓存。入口、CSS 和整个模块依赖图带一致版本；旧 worker 不得用旧脚本响应异版本查询。
6. 发布产物增加与 index.html 相同的 start.html，避开 0.6.3 之前 worker 对旧入口的缓存；新 worker 支持这个入口离线使用。同域本地用户与学习记录继续保留，不清理 localStorage 或 IndexedDB。

没有修改模型顶点、材质、热点或动画。GLB 本来已有 HTTP gzip；转 base64 JSON 实测 gzip 后反而大约增加 26%，因此未采用这种包装，也没有新增依赖或变更托管服务。

## 验证

- `tests/model-loader.test.js`：持续进度可超过短预算完成；无进度、独立总上限、取消、迟到响应与 HTTP 失败。
- `tests/offline-streaming.test.js`、`tests/offline-versioning.test.js`：阻塞/失败缓存写入不挡网络，后台完成后可离线使用；入口重验证、当前版本离线模块和异版本绕过旧缓存；start.html 离线入口。
- `tools/browser-model-transfer.cjs --local-only`：10 次真实 HTTP 调用，包括慢传原文件、慢传 gzip、停响应头、停响应体、总上限、取消、同 URL 重试和无 XHR 回退。成功场景均检查完整字节与 SHA256。
- `tools/browser-sw-streaming-probe.cjs`：实际生产 worker 的缓存写入被可控暂停时，页面已经获得完整模型，放行后后台缓存完成。
- 既有核心、引导、手机错误恢复与离线流程继续回归。Chrome 仿真通过后仍需用户在 iPhone 微信里用新入口实际确认；GitHub 链路本身有波动，不能仅凭本机测试宣布手机已恢复。

遵循 `$ub-mode`：根据手机反馈重新检查此前假设，先固定持续下载误杀与缓存门槛的失败案例，再做下载和缓存边界修改，保留原模型与存档格式。
